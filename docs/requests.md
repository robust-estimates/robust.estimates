# Коллекция запросов

[Импортируемая коллекция Postman v2.1](requests.postman_collection.json) содержит примеры всех 34 операций [OpenAPI 1.2.0](../api/public/openapi.yaml). Повторные GET и отдельная ветка ручного рассмотрения нужны для обновления версии и проверки разных исходов.

## Подготовка

1. Запустите проект из корня: `docker compose up --build -d --wait`.
2. В Postman выберите Import и файл `docs/requests.postman_collection.json`.
3. На вкладке Variables коллекции проверьте `baseUrl` (`http://localhost:8080/api/v1`) и `demoPassword`. Значение пароля по умолчанию соответствует `.env.example`; если пароль демонстрационных учёток другой, задайте его локально.
4. Выполните «Войти клиентом» и «Войти сотрудником». Скрипты ответов сохранят `clientToken` и `employeeToken` в переменные коллекции. Токены действуют один час; после истечения выполните вход заново.
5. В каждом запросе загрузки выберите свой непустой PDF/JPEG/PNG до 10 МиБ в `Body → form-data → file`. Для синтетической демонстрации можно использовать один и тот же файл в нескольких полях. Путь к личному файлу в коллекцию не включён.

Запросы создают синтетические аккаунты, компании, заявки и документы в выбранном API. Используйте локальный демонстрационный стенд. Не сохраняйте реальные токены и пароли в экспортируемой коллекции или Git.

## Основной маршрут

| Папка | Действия и ожидаемый результат |
|---|---|
| `01. Авторизация` | Войти клиентом и сотрудником. Регистрация необязательна; она переключает клиентский токен на новый аккаунт, поэтому после неё компанию нужно создать заново. |
| `02. Компания` | Создать профиль, получить его, обновить и подтвердить через локальный мок ФНС. `companyId` сохраняется автоматически. |
| `03. Каталог и подбор` | Получить продукты и карточку `unsecured`, выполнить подбор и расчёт для суммы 1 млн ₽ на 12 месяцев. |
| `04. Черновик и документы` | Создать и изменить заявку, загрузить финансовый отчёт и выписку, скачать файл. Дополнительный OTHER-документ загружается для демонстрации удаления. После каждого изменения документов перечитать заявку. Проверка комплектности должна вернуть `valid: true`. |
| `05. Решение, принятие и выдача` | Отправить заявку, дождаться решения, получить `offerId`, принять условия и смоделировать выдачу. Для исходных данных ожидается APPROVED, затем ACCEPTED и ISSUED. |
| `06. Банковский обзор` | Под токеном сотрудника получить очередь, карточку и скоринг заявки основного маршрута. |

Скоринг асинхронный: после submit повторяйте запрос «Дождаться решения» до выхода из SCORING. Только после этого получайте решение и принимайте предложение. Если заявка попала на MANUAL_CHECK из-за недоступности скоринга, автоматический маршрут потребует восстановления сервиса или решения сотрудника.

Не запускайте коллекцию целиком без остановок: загрузки требуют выбранных файлов, скоринг — ожидания, а некоторые действия взаимоисключающие. Для автоматического прогона используйте существующие команды проекта:

```sh
make e2e
make e2e-contract
```

## Ручное рассмотрение

Папка `07` создаёт отдельную синтетическую компанию с просрочкой и отдельную заявку. Её ID и версия сохраняются в `manualCompanyId`, `manualApplicationId` и `manualApplicationVersion`, поэтому она не перезаписывает переменные основного маршрута.

Выполняйте запросы папки по порядку:

1. Создайте и проверьте компанию, создайте заявку, загрузите финансовый отчёт и выписку.
2. Отправьте заявку. Повторяйте GET до MANUAL_CHECK.
3. Запросите дополнительные сведения от имени сотрудника. Статус станет NEEDS_INFO.
4. Получите список запросов. Скрипт сохранит `requestItemId` обязательного пункта.
5. Отправьте OTHER-файл с этим `requestItemId`, обновите версию через GET и повторно подайте заявку.
6. Снова дождитесь MANUAL_CHECK и выполните ручное одобрение.

Папка `08` содержит альтернативы. Банковское предложение других условий или отказ выполняются **вместо** ручного одобрения, пока заявка находится в MANUAL_CHECK. Отказ клиента выполняется **вместо** принятия предложения основного маршрута, пока заявка APPROVED или ALTERNATIVE. Для отмены создайте новый черновик; уже выданную заявку отменить нельзя.

## Переменные и заголовки

| Переменные | Назначение |
|---|---|
| `baseUrl`, `demoPassword` | Адрес API и локальный демонстрационный пароль |
| `clientToken`, `employeeToken` | Авторизация CLIENT и EMPLOYEE |
| `companyId`, `productId` | Компания основного маршрута и продукт; по умолчанию `unsecured` |
| `applicationId`, `applicationVersion` | Основная заявка и последняя прочитанная версия |
| `financialDocumentId`, `bankDocumentId`, `temporaryDocumentId` | Загруженные документы основного маршрута |
| `offerId` | Конкретное предложение из решения банка |
| `manualCompanyId`, `manualApplicationId`, `manualApplicationVersion` | Ресурсы отдельного ручного маршрута |
| `requestItemId` | Пункт запроса дополнительных сведений |

- Деньги передаются целыми копейками RUB: `100000000` — 1 млн ₽. Ставка `1690` — 16,9% годовых, срок `12` — 12 месяцев.
- В команды включён `Idempotency-Key: {{$guid}}`: при новом отправлении Postman создаёт новый ключ. Для повтора той же команды после потери ответа замените это выражение конкретным ключом исходного запроса и сохраните прежнее тело и `If-Match`. Новый ключ означает новое действие.
- Изменения существующей заявки и проверка комплектности передают `If-Match: "{{applicationVersion}}"` либо версию ручного маршрута. После загрузки/удаления документа обязательно выполняйте GET: ответ документа сам по себе не обновляет переменную версии заявки.
- При `409` перечитайте заявку и проверьте статус, версию и ключ. При `422` проверьте параметры и комплект документов.
- Для multipart не добавляйте `Content-Type` вручную: Postman формирует boundary. Для скачивания ответ содержит байты исходного документа.

Проверки ответов коллекции контролируют HTTP-статусы, сохраняют идентификаторы и версии; запрос validation дополнительно проверяет комплектность. Эти проверки не заменяют серверные unit-тесты и сквозные тесты проекта.
