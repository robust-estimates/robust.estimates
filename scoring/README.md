# Подключение к backend

gRPC-сервис запускается через корневой Compose. `app/model.py` преобразует protobuf Features в `schema.Application` и вызывает `risk.rules_v1.assess_risk`. Неизвестные данные собственника остаются None. Подробности преобразования признаков, ограничения и команды проверки — в [docs/integration.md](../docs/integration.md).

Ниже сохранены исходные заметки по развитию скоринга; не все описанные внешние источники и продуктовые сценарии подключены к текущему API.

### Какую задачу решаем

Я бы сформулировала так: **для каждого продукта из каталога оценить, подходит ли он клиенту и насколько вероятно одобрение, и выдать отранжированный список с пометками**.

Пометки «рекомендуем / подходит / не подходит» — это классификация поверх того же скора по порогам. Фронт подсвечивает верх списка, а клиент всё равно может выбрать любой продукт.

### Вход

**Что вводит клиент** (коротко, чтобы не отпугнуть на старте):

- цель кредита: выбор из списка или свободный текст;
- желаемая сумма и срок (можно «не знаю, подберите»);
- выручка за последний год или средняя за месяц;
- текущие кредитные платежи в месяц;
- есть ли залог (по желанию).??

**Что подтягивается само по ИНН** (из моков):
- из ЕГРЮЛ: возраст бизнеса, ОКВЭД (отрасль), регион, форма (ИП / ООО);
- из ФНС: налоговые долги, отчётность;
- из БКИ: кредитная история компании и собственника;
- если клиент уже обслуживается в банке: обороты по счёту.


**Каталог продуктов**: у каждого продукта цели, мин/макс сумма, срок, ставка и требования.

### Модель риска вызывается дважды:

- **До заявки, для рекомендации:** предварительная оценка по тому, что клиент успел ввести, плюс данные по ИНН. Это «мягкий» прогноз шансов.
- **После подачи:** полная оценка по всем данным, на её основе принимается решение.

### Идея для использования LLM: подбор продукта по описанию задачи своими словами**

**Проблема**  
Предприниматель не знает банковских названий продуктов. Он знает, что ему нужно: «купить второй фургон», «закрыть кассовый разрыв до оплаты от заказчика». Список «оборотный кредит / инвестиционный кредит / овердрафт» ему ни о чём не говорит, поэтому он может выбрать неподходящий продукт или бросить заявку.

**Решение**  
Клиент описывает цель своими словами. LLM переводит текст в категорию цели, а по категории система определяет, какие продукты из каталога подходят.
### Шансы на одобрение показываем словами, а не процентом**

**Проблема**  
Клиент выбирает продукт и сумму, но не понимает, одобрят ли ему кредит. Он узнаёт это только после подачи, и отказ становится неприятным сюрпризом. Если же показать точный процент («вероятность одобрения 73%»), клиент воспримет его как обещание банка и будет разочарован, если решение окажется другим.

**Решение**  
Рядом с каждым продуктом и при изменении суммы или срока показываем шансы на одобрение одним из трёх уровней:

- **Высокие шансы.** Продукт и сумма хорошо подходят вашему бизнесу.
- **Средние шансы.** Возможно одобрение, но банк может предложить другие условия.
- **Низкие шансы.** Скорее всего, понадобится меньшая сумма, другой срок или дополнительные документы.


#### Выход

Скоринг возвращает два блока: **оценку клиента** (для банка) и **подборку продуктов** (для клиента).

**Оценка клиента** (видит только сотрудник банка):

- **Риск** — вероятность того, что клиент не вернёт кредит (число от 0 до 1). Единственный результат ML-модели, всё остальное строится на нём.
- **Факторы** — что повлияло на риск и насколько: признак, его значение и вклад со знаком («долговая нагрузка 42%: повышает риск»). Нужны андеррайтеру, чтобы понять и проверить оценку.

**Подборка продуктов** (видит клиент):

Все продукты каталога раскладываются по трём группам. Принадлежность к группе и порядок внутри неё уже содержат рекомендацию, поэтому отдельные пометки и номера мест не нужны.

- **Рекомендуем** — 1–2 продукта, которые подходят под цель клиента и имеют лучшие шансы на одобрение. Фронт подсвечивает их.
- **Доступны** — остальные продукты, которые клиент может выбрать. Отсортированы от более подходящих к менее подходящим.
- **Недоступны** — продукты, требованиям которых клиент не соответствует (например, возраст бизнеса меньше минимального) или которые не предназначены для его цели.

Для каждого продукта из групп «Рекомендуем» и «Доступны»:

- **Шансы на одобрение** — высокие / средние / низкие, для предложенных суммы и срока.
- **Сумма** — сколько банк готов предложить по этому продукту.
- **Срок** — на сколько месяцев.
- **Причина** — одна фраза простым языком: почему продукт здесь и почему такая сумма («Подходит для покупки транспорта. Сумма снижена, чтобы платёж был комфортным»).

Для продуктов из группы «Недоступны» — только **причина**: почему продукт нельзя выбрать.

Ежемесячный платёж не возвращается: фронт считает его сам из суммы, срока и ставки продукта из каталога. Так он всегда совпадает с тем, что клиент видит при изменении суммы и срока.

**Предварительная и финальная оценка**

Выход одинаковый в обоих случаях. Различаются только полнота данных и то, что происходит дальше:

- **до подачи** подборка помогает клиенту выбрать продукт, и статус заявки не меняется;
- **после подачи** движок политики превращает оценку в решение по заявке: одобрено, контрпредложение, ручная проверка или отказ.

1. **Вход:** собираем анкету клиента и подтягиваем данные по ИНН.
2. [ML] **Категория цели:** относим цель кредита к одной из 6–8 категорий (классификация текста).
3. **Признаки клиента:** считаем признаки из анкеты и данных по ИНН.
4. **Для каждого продукта каталога:**
    - **Требования:** проверяем, проходит ли клиент требования продукта.
    - **Сумма и срок:** подбираем наибольшую сумму, которая укладывается в платёжеспособность и допустимый риск.
    - **[ML] Риск:** бинарная классификация → **WoE + логистическая регрессия**; для сравнения — бустинг (CatBoost / LightGBM).
    - **Шансы:** переводим вероятность в уровень «высокие / средние / низкие».
5. **Группы и порядок:** раскладываем продукты на «Рекомендуем», «Доступны» и «Недоступны» и сортируем.
6. [ML?] **Причины:** формулируем для каждого продукта одну фразу объяснения (генерация текста; без ML — по шаблонам).
## Разработка

```
scoring/
├── schema.py          — общий формат анкеты (Application), меняем только по договорённости
├── risk/
│   ├── rules_v1.py    — экспертная балльная карта (бейзлайн), ответ в формате Scoring
│   └── metrics.py     — Gini / ROC AUC
├── data/
│   └── generator.py   — синтетические компании с меткой дефолта
├── affordability/     — CFADS, DSCR, допустимая сумма (см. draft.md)
└── tests/
```

Нужен Python 3.12.

```bash
cd scoring
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.lock
.venv/bin/pytest
.venv/bin/python -m data.generator --n 20000 --seed 42
```

Генератор сохраняет данные в `data/generated/companies.csv` (не коммитится) и печатает Gini `rules-v1` и потолок — Gini истинной вероятности дефолта, заложенной в генератор. На 20 000 компаниях с seed 42: доля дефолтов 6,0%, Gini `rules-v1` 0,449, потолок 0,554.
