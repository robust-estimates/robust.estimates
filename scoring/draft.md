# Скоринг и подбор кредитных продуктов — MVP

**Статус:** спецификация демонстрационного прототипа

MVP использует синтетические данные и моки ФНС/БКИ/банковских оборотов. Он не принимает реальные кредитные решения и не оценивает настоящую вероятность одобрения.

## 1. Принятые допущения MVP

Все значения ниже — временные параметры прототипа. Хранить их в версионируемой конфигурации, не зашивать в код.

| Параметр | Значение |
|---|---:|
| Финансовый период | месяц |
| Минимальный базовый DSCR | `1.20` |
| Снижение CFADS в стресс-сценарии | `20%` |
| Минимальный стрессовый DSCR | `1.00` |
| LTV залога для синтетических тестов | `0.60` |
| Минимальная выборка для статистической подсказки | `30` наблюдений |
| Минимальная сумма контрпредложения менеджера | `30%` от запрошенной суммы |

**Правила:** если выборка меньше 30 — расширить сегмент; если данных всё ещё недостаточно, статистическую подсказку скрыть. Статистическая медиана не ограничивает сумму автоматически. При неизвестных обязательных данных не подставлять ноль. Если для продукта не настроена подходящая модель платежей, вернуть `INSUFFICIENT_DATA` или `MANUAL_REVIEW`.

## 2. Входные данные и этапы

**Клиент вводит:** цель (список или свободный текст), желаемую сумму и срок, выручку, расходы/денежный поток, текущие долговые платежи; сведения о залоге — для залоговых продуктов. Сумма и срок могут быть необязательны на этапе подбора.

**Моки по ИНН:** возраст бизнеса, ОКВЭД, регион, форма ИП/ООО; налоговые долги и отчётность; кредитная история компании и собственника; обороты по счёту. Для каждой величины сохранять источник и период. До соответствующих проверок учитывать согласия.

Оценка запускается дважды:
1. **До подачи:** предварительный подбор по доступным данным; статус заявки не меняется.
2. **После подачи:** полная проверка и расчёт; результат передаётся в политику заявки: `APPROVED`, `COUNTER_OFFER`, `MANUAL_REVIEW` или `REJECTED`.

## 3. Последовательность скоринга

1. Нормализовать анкету и данные из моков.
2. Определить категорию цели (LLM допустима для классификации текста; не для расчёта условий).
3. Для каждого продукта проверить обязательные требования.
4. Для прошедших проверку продуктов рассчитать платёжеспособность и допустимую сумму отдельным обработчиком продукта.
5. Проверить стресс-сценарий и применить продуктовые/залоговые ограничения.
6. Сформировать группы `RECOMMENDED`, `AVAILABLE`, `UNAVAILABLE`, причины и сортировку.
7. Сохранить входные данные, версии правил и результат.

## 4. Финансовые формулы

Все величины приводятся к месячному периоду. Методика расчёта CFADS должна быть единой и версионируемой; конкретный состав статей отчётности для MVP задаётся в коде/конфигурации и явно документируется.

### 4.1. Денежный поток и DSCR

$CFADS = \text{денежный поток, доступный для обслуживания долга за месяц}$

$DSCR = \frac{CFADS}{D_{existing} + D_{new}}$

где $D_{existing}$ — текущие ежемесячные долговые платежи, $D_{new}$ — платёж по новому продукту. Если обязательные финансовые данные отсутствуют, сумму не рассчитывать.

### 4.2. Допустимый платёж по новому долгу

Из условия $DSCR \geq 1.20$:

$D_{new,max} = \frac{CFADS}{1.20} - D_{existing}$

Если $CFADS \leq 0$ или $D_{new,max} \leq 0$, положительный лимит не выдавать.

### 4.3. Аннуитетный кредит

Применять только к продуктам, для которых в конфигурации явно задана аннуитетная модель. При сумме кредита $P$, месячной ставке $r$ и количестве платежей $n$:

$A = P \cdot \frac{r(1+r)^n}{(1+r)^n-1}$

Если годовая номинальная ставка $i$, то $r=i/12$. При нулевой ставке $A=P/n$.

Обратный расчёт суммы при допустимом платеже $A_{max}$:

$P_{max} = A_{max} \cdot \frac{(1+r)^n-1}{r(1+r)^n}$

При $r=0$: $P_{max}=A_{max}\cdot n$.

### 4.4. Стресс-сценарий

$CFADS_{stress}=CFADS\cdot(1-0.20)$

$DSCR_{stress}=\frac{CFADS_{stress}}{D_{existing}+D_{new}}$

Требование: $DSCR_{stress}\geq1.00$. Если условие не выполняется, уменьшить сумму и пересчитать. Если подходящую сумму определить нельзя — `INSUFFICIENT_DATA` или `MANUAL_REVIEW`, а не обещание одобрения.

## 5. Итоговая сумма и статистика

Для стандартного кредита:

$P_{final}=\min(P_{requested},P_{capacity},P_{product\_max},P_{collateral})$

$P_{collateral}$ учитывается только для продуктов, где залог применим, принят и оценён; для незалоговых продуктов ограничение не применяется. Если рассчитанная сумма ниже минимальной суммы продукта, продукт не предлагать с искусственно увеличенной суммой.

**Статистическая подсказка:** медиана сумм одобренных синтетических/тестовых заявок по похожему сегменту (цель × продукт × тип бизнеса × возраст бизнеса × группа выручки). При достаточном числе наблюдений можно показывать Q25/Q50/Q75. При малом сегменте расширить его; если данных всё ещё недостаточно — скрыть подсказку. Всегда подписывать: «Статистический ориентир по похожим заявкам; не гарантирует одобрение». Не называть сумму «наиболее вероятной к одобрению».

**Контрпредложение менеджера:** разрешено уменьшить исходный запрос до 30%, но нельзя превысить рассчитанный лимит или ограничения продукта. Если допустимого интервала нет — заблокировать. Сервер повторно проверяет сумму, срок, ставку и платёж; требуется причина изменения, исходные условия сохраняются.

## 6. Отдельные обработчики 12 сценариев

Общий скоринг не заменяет продуктовую логику. Для каждого сценария нужен отдельный обработчик и соответствующая модель платежей.

1. **Кредит без залога:** разовая выдача; лимиты суммы/срока, финансовый расчёт, требования к поручителю.
2. **Кредит с залогом:** финансовый расчёт плюс тип/собственник/стоимость/обременения залога.
3. **Возобновляемая линия без залога:** лимит, транши, погашение и восстановление доступного лимита по правилам продукта.
4. **Возобновляемая линия с залогом:** логика возобновляемой линии плюс проверка залога.
5. **Невозобновляемая линия с залогом:** выдачи траншами; погашение не восстанавливает доступный лимит; обязательна проверка залога.
6. **«Деньги на дело»:** отдельные требования к ликвидному залогу, оценке и возрасту бизнеса.
7. **Бизнес-ипотека:** цель покупки недвижимости, объект, продавец и оформление объекта в залог.
8. **Овердрафт:** история поступлений на счёт, краткосрочный кассовый разрыв и погашение из поступивших средств.
9. **Кредит продавцу:** продажи на маркетплейсе, выплаты, возвраты, комиссии и подтверждение оборотов.
10. **Рефинансирование:** перечень рефинансируемых кредитов, остатки задолженности, условия и исключения.
11. **Господдержка:** конкретная программа и версия, период действия и дополнительные критерии.
12. **Business One Credit:** карточный лимит, транзакции, обязательства и льготный период согласно тарифу.

Не применять аннуитетную формулу к овердрафту, линиям или карте без явной настройки соответствующей модели. Если точные правила продукта неизвестны, не додумывать их: возвращать `MANUAL_REVIEW`/`INSUFFICIENT_DATA`.

## 7. Проверка соответствия и цель

Примеры кодов причин: `PURPOSE_NOT_SUPPORTED`, `AMOUNT_OUT_OF_RANGE`, `TERM_OUT_OF_RANGE`, `BUSINESS_AGE_REQUIREMENT_NOT_MET`, `COLLATERAL_REQUIRED`, `MISSING_REQUIRED_DATA`, `PROGRAM_NOT_ACTIVE`.

Стартовые категории цели: оборотные средства; кассовый разрыв; оборудование/транспорт; недвижимость; развитие бизнеса; рефинансирование; закупка товаров; другое/не определено. Если классификация свободного текста неуверенная — задать уточняющий вопрос. Требования берутся из версионируемого каталога; критерии одного продукта не переносить автоматически на другие.

## 8. Результат для клиента и сотрудника

**Клиенту:**
- `RECOMMENDED` — 1–2 наиболее подходящих продукта;
- `AVAILABLE` — другие продукты, прошедшие обязательные требования, отсортированные по соответствию цели и финансовой вместимости;
- `UNAVAILABLE` — продукты, которые не проходят требования, с конкретной причиной.

Для `RECOMMENDED` и `AVAILABLE` возвращать продукт, сумму, срок, уровень оценки и простую причину. Уровни «высокие/средние/низкие шансы» допустимы только как **эвристическая категория соответствия**, а не как подтверждённая вероятность одобрения. Пока нет размеченных реальных исходов, не показывать проценты и не обещать одобрение. Если данных мало, показать «недостаточно данных для расчёта».

**Сотруднику:** риск-оценка и факторы, повлиявшие на неё, только если есть обоснованная модель; в MVP допустимы прозрачные правила и причины. Не выдавать случайное число 0–1 за вероятность дефолта.

Причины генерировать из фактически сработавших правил и расчётов. LLM может переформулировать объяснение, но не определяет сумму, ставку, требования или решение.

**Платёж:** интерфейс может пересчитывать его для удобства, но сервер обязан валидировать и пересчитывать сумму, срок, ставку и платёж при каждом изменении.

## 9. ML — следующий этап, не ядро MVP

Коллега предложила бинарную модель риска: WoE + логистическая регрессия; CatBoost/LightGBM — для сравнения. Это кандидаты на будущий эксперимент, но обучение требует реальных размеченных исходов и заданного горизонта дефолта. Синтетические метки можно использовать для проверки интеграции, но нельзя выдавать как реальную статистику. Будущая модель должна иметь версию, описание признаков, валидацию, метрики и объяснимость; она не отменяет продуктовые ограничения и проверку платёжеспособности.

## 10. История, API и тесты

Для каждого расчёта сохранять: ID заявки/продукта; входные значения и источники; время; версии каталога, правил и финансовой методики; параметры DSCR/стресса/LTV; CFADS, текущие платежи, DSCR и стрессовый DSCR; допустимый платёж и сумму; причины и статус; исходные условия и изменения менеджера.

Изменение каталога не меняет старые заявки. Изменение финансовых данных создаёт новый результат и сохраняет предыдущий. Один набор данных и одна версия правил должны давать воспроизводимый результат.

Backend-ответ должен содержать минимум: `application_id`, `scoring_version`, `calculated_at`, `overall_status`, финансовые показатели, список продуктов (`product_id`, группа, `eligible`, запрошенная/рассчитанная сумма, срок, платёж, `amount_status`, `reason_codes`, объяснение) и предупреждения. Точную JSON/OpenAPI-схему согласовать с Go-разработчиком.

**Минимальные тесты:** недостаток данных; отрицательный CFADS; текущие платежи выше допустимых; сумма выше/ниже лимита продукта; провал стресса; недостаточная статистическая выборка; восстановление лимита возобновляемой линии и отсутствие восстановления у невозобновляемой; отсутствие аннуитетной модели у нестандартного продукта; пересчёт при смене суммы/срока; запрет менеджеру превысить лимит; сохранение истории версий.

## 11. Что нельзя считать подтверждённым

До появления надёжных источников отдельно подтвердить: состав CFADS; актуальные лимиты/сроки/ставки и критерии каждого продукта; правила оценки залога; модели траншей и платежей; доступность и полноту источников данных; статистическую методику. Публичные условия и значения «от» не равны индивидуальным условиям клиента.

**Порядок реализации:** соответствие продукта → финансовая вместимость → ограничения суммы → объяснимое ранжирование. Статистика показывается только при достаточной выборке; ML-вероятности не имитируются без обучающих данных.
