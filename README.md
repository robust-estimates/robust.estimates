# robust.estimates

Учебный кредитный конвейер для хакатона: три Go-сервиса, Python-скоринг, PostgreSQL и S3-совместимый MinIO. Frontend подключается к REST API gateway. Между backend-сервисами используется gRPC.

## Интеграция frontend и ML

Frontend подключён к API, Python gRPC вызывает модуль риска коллег. Запуск всего проекта: `make up`, интерфейс: http://localhost:3000. [Сценарии, контракты и проверки](docs/integration.md).

## Для команды

[Карта файлов, подключение frontend и ML](docs/team-guide.md).

## Запуск

Нужны Docker Engine / Docker Desktop и Docker Compose v2. Первой сборке нужен интернет; MinIO собирается из зафиксированного официального исходного кода, поэтому она может занять несколько минут. Go и Python на хосте для запуска контейнеров не нужны.

```sh
cp .env.example .env
docker compose up --build -d --wait
```

Адреса:

- Интерфейс: http://localhost:3000

- API: http://localhost:8080/api/v1
- Swagger UI: http://localhost:8080/docs/
- OpenAPI: http://localhost:8080/openapi.yaml
- Проверка готовности: http://localhost:8080/readyz
- MinIO Console: http://localhost:9001

Swagger UI загружает JS/CSS из unpkg, для просмотра документации нужен интернет. Сам API не зависит от CDN. YAML можно открыть и в своём Swagger UI.

```sh
docker compose logs -f gateway application-service
docker compose down
```

`down` сохраняет volumes с БД и файлами. Удаление volumes удалит данные. Шаг `database-init` перед стартом сервисов создаёт отсутствующие БД/роли и синхронизирует пароли `company_user`, `application_user`, `auth_user` с `.env`. Существующие таблицы и файлы сохраняются. Административный `POSTGRES_PASSWORD` при сохранённом volume должен соответствовать уже установленному паролю администратора; его ротация выполняется отдельно. Смена `DEMO_PASSWORD` не меняет пароли уже созданных тестовых учёток.

## Демонстрационные учётные записи

| Логин | Роль |
|---|---|
| client@demo.local | Клиент |
| other@demo.local | Другой клиент для проверки разграничения доступа |
| employee@demo.local | Сотрудник банка |

Пароль задаётся `DEMO_PASSWORD`; в `.env.example` это `Demo-Credit-2026!`. JWT действует один час, затем требуется новый вход. Учётки синтетические. При внешнем развёртывании отключите `SEED_DEMO` и замените демонстрационные секреты; начальная версия входа не реализует refresh, восстановление пароля и интеграцию OIDC.

### Как войти сотрудником банка

1. Запустите проект командой `make up` и откройте [интерфейс](http://localhost:3000).
2. Если уже вошли как клиент, откройте меню профиля справа сверху и нажмите **«Выйти»**.
3. На странице входа введите:

   ```text
   Email: employee@demo.local
   Пароль: Demo-Credit-2026!
   ```

4. Нажмите **«Войти»**. Откроется кабинет сотрудника банка с очередью заявок: [http://localhost:3000/#/specialist](http://localhost:3000/#/specialist).
5. Выберите заявку, чтобы посмотреть результаты скоринга и документы, запросить дополнительные сведения, одобрить заявку, предложить другие условия или отказать. Доступные действия зависят от статуса заявки.

Учётная запись сотрудника создаётся при первом запуске с `SEED_DEMO=true`. Если перед первым запуском вы изменили `DEMO_PASSWORD` в `.env`, используйте заданный пароль. Изменение этой переменной после создания учётки не обновляет её пароль. Обычная регистрация создаёт только клиента; переход по ссылке кабинета не выдаёт роль сотрудника.

Пример входа через API:

```sh
curl -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"client@demo.local","password":"Demo-Credit-2026!"}'
```

Токен из `accessToken` передавайте как `Authorization: Bearer ...`. В Swagger нажмите Authorize и вставьте токен.

## Сквозная проверка

После запуска контейнеров выполните:

```sh
python3 scripts/e2e.py
```

Скрипт использует только стандартную библиотеку Python, создаёт синтетические компании/заявки/файлы и проверяет:

- авторизацию и недоступность чужих компаний, заявок и документов;
- подбор продукта без заранее известной суммы и корректность графика;
- обязательность документов и фактический MIME файла;
- загрузку PDF в S3 и скачивание с совпадением содержимого;
- автоматическое одобрение, принятие и выдачу-мок;
- повтор выдачи с тем же ключом и запрет второй выдачи с новым ключом;
- повтор загрузки после выдачи, конфликт другого содержимого с тем же ключом и повтор удаления;
- альтернативную сумму и отказ клиента;
- ручную проверку, запрос дополнительных документов, повторную отправку и отказ банка;
- отмену заявки и обновление ленты.

Скрипт добавляет данные, не очищает чужие записи. По умолчанию использует API на localhost:8080 и пароль из корневого `.env`, либо `DEMO_PASSWORD` из окружения. Другой адрес задаётся через `API_URL`.

## Структура

```text
robust.estimates/
├── gateway/                 REST, вход, gRPC clients
├── company-service/         профили, финансы, продукты, рекомендации, калькулятор
├── application-service/     заявки, документы, решения, worker, история, лента
├── scoring/                 Python gRPC, rules-v1, точка подключения ML
├── contracts/               сгенерированные Go protobuf bindings
├── platform/                инфраструктура и отдельный пакет core без инфраструктурных импортов
├── api/public/openapi.yaml  внешний контракт
├── api/proto/credit/v1/     внутренние контракты
├── deploy/                  PostgreSQL init, сборка MinIO
├── scripts/                 E2E, генерация контрактов
├── testdata/                синтетические сценарии
├── docs/                    архитектура, ограничения, Swagger
├── compose.yaml
└── go.work
```

У каждого Go-сервиса свой модуль. `domain` содержит сущности и правила, `usecase` - сценарии и порты, `adapter` - PostgreSQL, S3, gRPC/HTTP. `cmd/server` собирает зависимости. Сгенерированные protobuf-типы не импортируются доменом и сценариями. Пакет `platform/core` содержит только контекст пользователя/команды, ошибки и небольшие функции стандартной библиотеки. `platform` содержит транспорт и инфраструктуру; это не общий пакет бизнес-моделей.

Go: версия языка 1.27.0, Docker builder 1.27.3. Python image: 3.13.9. Библиотеки зафиксированы в go.mod/go.sum и scoring/requirements.txt. PostgreSQL в Compose - 17.6.

## Договорённости API

Внешний контракт - `api/public/openapi.yaml` версии 1.2.0, 34 операции. Внутренний - `api/proto/credit/v1/credit.proto`.

- Деньги: целые копейки RUB. `100000000` означает 1 млн рублей.
- Ставки: базисные пункты. `1690` означает 16,9% годовых.
- Время: UTC, RFC3339. Идентификаторы - непрозрачные строки.
- Для POST/PATCH/DELETE, кроме входа и регистрации, нужен `Idempotency-Key` длиной 8–128.
- Для изменения существующей заявки также нужен `If-Match: "3"`, где 3 - текущая version.
- GET заявки и ответы с заявкой содержат ETag. После загрузки/удаления документа получите свежую version через GET.
- Повтор команды с тем же ключом и телом возвращает исходный результат до проверки версии. Другое тело с тем же ключом - 409. Хранение ответа - 24 часа.
- Рекомендации, расчёт и validation являются чтением: ключ требуется единообразным транспортным контрактом, но ответ не кэшируется как команда.
- Чужие ресурсы возвращают 404; клиентские вызовы банковских методов - 403.
- PATCH компании заменяет профиль целиком, сбрасывает проверку ФНС; ИНН неизменяем.
- Компания заявки неизменяема. Продукт можно менять в черновике, после отправки - нельзя.
- Входящие JSON принимают только известные поля protobuf-контракта.

Frontend должен обновить свой контракт относительно первоначального YAML: добавлены данные представителя, калькулятор, группы рекомендаций, фильтры очереди, скачивание файлов, запросы сведений, обзор сотрудника и отображаемый номер заявки. Сумма подбора необязательна; в отправляемой заявке - обязательна. Разрешённые сроки и суммы зависят от продукта.

## Документы и данные

Файлы: PDF/JPEG/PNG до 10 МиБ. Gateway ограничивает весь multipart-запрос, временно сохраняет крупные части в системный temp и удаляет их после запроса; дальше передаёт файл gRPC-потоком по 64 КиБ. Application service проверяет содержимое, рассчитывает SHA-256 и сохраняет объект в закрытый bucket. В БД - метаданные и ключ объекта. XLSX/DOCX/PPTX пока не поддерживаются.

Неудачные загрузки остаются STAGED и удаляются reconciler после часа; удалённые документы помечаются DELETING и чистятся в фоне. Метаданные и S3 не объявляются общей транзакцией.

В одном экземпляре PostgreSQL созданы `company_db`, `application_db`, `auth_db` и отдельные роли. Доступ к чужим таблицам не нужен. Миграции запускаются при старте под advisory lock, сохраняют checksum в schema_migrations. Применённую миграцию не редактируйте - добавляйте следующую.

## Обработка

Application service - единственный владелец статуса заявки. Worker получает задания из PostgreSQL с lease и SKIP LOCKED, вызывает Python через gRPC и применяет результат только к ожидаемой версии заявки. Задание и SCORING сохраняются одной транзакцией. После сбоя - повтор, максимум три попытки, затем ручная проверка. Отменённая заявка не возобновляется поздним результатом.

Python содержит явно названный rules-v1, а не обученную ML-модель. Модель оценивает возраст бизнеса, выручку, расходы, долговые платежи, данные ФНС, кредитную историю из БКИ и обороты по счёту. Возвращает риск, рекомендацию и доступную сумму по DSCR (`scoring/affordability/dscr.py`). Решение учитывает продукт и эту сумму; средний/высокий риск направляются сотруднику. gRPC-адаптер `scoring/app/model.py` вызывает `risk.rules_v1.assess_risk` из модуля коллег. ML-разработчик меняет модель риска и её версию при сохранении gRPC-контракта; подробности подключения — в `docs/integration.md`.

## Конфигурация

| Переменная | Назначение |
|---|---|
| JWT_SECRET | HS256-подпись внешней и внутренней идентичности, минимум 32 символа |
| DATABASE_URL | Собственная база каждого сервиса |
| COMPANY_GRPC_ADDR / APPLICATION_GRPC_ADDR / SCORING_GRPC_ADDR | Внутренние адреса |
| S3_ENDPOINT / S3_ACCESS_KEY / S3_SECRET_KEY / S3_BUCKET | S3-хранилище |
| S3_SECURE | true для HTTPS до S3 |
| CORS_ORIGIN | Разрешённый origin frontend, по умолчанию localhost:5173 |
| DEMO_PASSWORD / SEED_DEMO | Синтетические учётки |
| HTTP_ADDR / GRPC_ADDR | Адрес прослушивания |
| MIGRATIONS_DIR | Папка SQL-миграций |

Compose публикует API и консоль S3 только на localhost; внутренние gRPC и PostgreSQL на хост не опубликованы. Внутренний транспорт в локальной сети Compose без TLS, с проверкой JWT. Для внешней/корпоративной среды нужны HTTPS на входе, mTLS/сервисные идентичности и отдельные S3-права; демонстрационные root-credentials MinIO предназначены для локального запуска.

## Границы MVP

ФНС, БКИ и обороты по счёту - локальный мок-сервис `mocks/` с синтетическими данными по ИНН (профили для демонстрации - `mocks/profiles.json`); реальные SMS, внешняя авторизация, подписание и денежные переводы отсутствуют. Ручная проверка доступна всем тестовым сотрудникам, детальная модель назначений отделов ещё не вводилась. Компания принадлежит одному тестовому пользователю; делегирование полномочий и приглашения не реализованы. Профиль хранит текущие финансовые показатели; отдельный архив периодов не реализован.

Документы не проходят антивирус; поддержка дополнительных форматов и карантина - следующий этап. Лента содержит актуальные состояния последних 100 заявок и встроенную рекомендацию, без внешнего новостного провайдера. Redis, Kafka, Patroni/etcd/HAProxy и Prometheus/Grafana в этот MVP не включены. Точки расширения описаны в docs/architecture.md.

Frontend не изменён. Backend можно проверять через Swagger и E2E, затем подключать экраны команды.

## Ошибка password authentication failed для служебной роли

```sh
docker compose up -d --wait
docker compose logs --tail=50 database-init company-service
```

`database-init` должен завершиться с кодом 0. Если нужно повторно выполнить его вручную после исправления окружения:

```sh
docker compose run --rm database-init
docker compose up -d --wait
```

Для исправления паролей удалять volumes не требуется. Если ошибка относится к администратору `postgres`, проверьте первоначальный пароль сохранённого volume.

## Подробная консольная проверка API

```sh
python3 scripts/check_api.py --verbose --extended --report api-report.json
```

Стандартная библиотека Python 3, дополнительных зависимостей нет. Проверяются все 34 текущие операции API: роли, компании, профиль, продукты, подбор, калькулятор, черновики, документы, выдача, история, лента, альтернативы, ручные решения и отмена. Скрипт создаёт синтетические данные, существующие записи не удаляет. Токены и пароль не выводятся и не включаются в отчёт. Код выхода 0 означает успех, 1 - ошибку проверки.

`--verbose` показывает HTTP-запросы, `--extended` добавляет загрузку файла больше 10 МиБ. `--base-url` переопределяет адрес API, `--env-file` - путь к файлу окружения, `--wait-seconds` - срок ожидания одного решения скоринга. Пароль берётся из DEMO_PASSWORD окружения или .env.

## Финальная проверка перед отправкой

```sh
make check
```

Нужны Make, Go, Python >= 3.10 и работающий Docker Engine. Makefile выбирает доступный Python 3.13/3.12/3.11/3.10; при необходимости задайте `PYTHON=/path/to/python3`. Для Go зафиксирован GOTOOLCHAIN=go1.27.3. При первой проверке потребуется интернет для зависимостей и сборки образов.

Команда проверяет форматирование Go, go vet, Go-тесты с race, сборку трёх сервисов, Python-тесты текущего скоринга, OpenAPI, Compose, готовность API и два сквозных сценария: 34 операции через консольный проверяющий скрипт и ответы по OpenAPI. Тестовые зависимости ставятся в `.venv`, существующий `.env` сохраняется. Бинарники и JSON-отчёт лежат в игнорируемой папке build/. Существующие БД и S3-файлы не удаляются; E2E добавляют синтетические данные. Контейнеры после успешной проверки остаются работать.

```sh
make check-go
make e2e E2E_FLAGS="--verbose --extended"
make status
make logs
make down
```

`make check-go` проверяет только Go-код без Docker и Python-скоринга. Это удобно для проверки своей части при раздельной работе над ML. `make help` выводит остальные команды. Изменение API_URL направляет интеграционные проверки на указанный API; `make up` при этом запускает локальный Compose.

Если загрузка Docker-образов завершается `Keychain Error. (-67674)`, проблема возникает в доступе Docker к macOS Keychain до старта приложения. Запустите команду из обычного терминала с доступной связкой ключей. Makefile не меняет Docker credentials и останавливает проверку с ошибкой. `make check-go` можно выполнить независимо от Docker.

## Регистрация клиента

`POST /api/v1/auth/register` - публичный метод, токен и Idempotency-Key не требуются.

```sh
curl -X POST http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"login":"new-client@example.com","displayName":"Иван Иванов","password":"My-Credit-2026!"}'
```

Ответ 201 содержит accessToken, tokenType=Bearer, expiresIn=3600 и role=CLIENT. Токен сразу подходит для /me, создания компаний и заявок. После этого вход выполняется через /auth/login с теми же login/password.

Email нормализуется в нижний регистр, пробелы по краям удаляются. Повтор email, включая другой регистр, даёт 409. Имя - от 2 до 100 символов, пароль - минимум 12 символов и максимум 72 байта UTF-8. Пароль сохраняется только в виде bcrypt-хеша. Неизвестные поля, в том числе role, отклоняются с 400. Самостоятельная регистрация EMPLOYEE/SYSTEM не предусмотрена. В MVP подтверждение email не выполняется.

Миграция gateway/002_login_case_insensitive.sql добавляет уникальный индекс lower(login), не меняя применённый 001_init.sql. Ограничение регистрации - 20 запросов в минуту на IP, входа - 10; лимиты независимы. make e2e проверяет регистрацию, повторный вход и запрет повышения роли; make e2e-contract проходит кредитный сценарий с зарегистрированным клиентом.

Для обновления запущенного gateway:

```sh
docker compose up --build -d --wait gateway
```
